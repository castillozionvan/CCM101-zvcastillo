# Mission 7 Reflection: Cloud Operations & Observability

Throughout this mission, I gained practical insight into Site Reliability Engineering by learning that monitoring the host server's CPU, RAM, and disk storage is just as vital as checking individual container health, as a resource-exhausted host will trigger kernel panics or the Out-Of-Memory killer and crash every container sharing its hardware. When troubleshooting web application issues like failed user logins, commands like `docker logs` provide essential visibility by displaying exact HTTP status codes (such as `401 Unauthorized` or `500 Internal Server Error`), exception stack traces, and database connection timeouts that pinpoint whether the glitch stems from invalid credentials or a backend failure. This highlighted the fundamental difference between logs and metrics: logs act as discrete, event-driven textual records explaining *what* specific action or error occurred at a given time, whereas metrics provide aggregated, numerical time-series data like CPU percentage and memory footprint that show *how* system resources perform under load. On an enterprise scale, managing thousands of microservices requires moving beyond manual CLI tools toward automated observability pipelines, where tools like Prometheus scrape real-time metrics and log collectors like Loki or Fluentd aggregate log streams into centralized Grafana dashboards for proactive alerting. Ultimately, stepping through system baselines, log extraction, and live metric streams has transformed my approach to Linux system administration—moving me away from visual guesswork toward evidence-based troubleshooting using concrete terminal metrics.
